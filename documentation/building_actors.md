# Building Actors

As discussed in the README, an Actor consists of a Starlark-based description and a Rust crate implementing its Behavior.

One can bootstrap a new Actor using [cargo-generate](https://github.com/cargo-generate/cargo-generate):
```
cargo generate --git https://github.com/edgeless-project/nextless templates/actor
```

The Actor can be built using `edgeless_cli`:
```
edgeless_cli -c ../path_to_config/cli.toml function build example_actor_1/example_actor_1.star
```
This will result in a file `example_actor_1/example_actor_1.wasm`.

Note that one needs to use edgeless_cli for the first build after a change to the Starlark description, as the Rust macros depend on the file `function.json` generated from the Starlark description.  
One can use `cargo build`/`rust-analyzer` after `function.json` has been generated.

## Starlark-Based Actor Description

An Actor is primarily described using Starlark.  
As this is a building block that can be instantiated in many applications, what we're actually building here is an `Actor Class`:

```star
DemoFilter = edgeless_actor_class(
    id = "demo_filter",
    version = "0.1",
    outputs = [
        cast_output("accepted_out", "eft.eval.mock_sensor_value"),
        cast_output("rejected_out", "eft.eval.mock_sensor_value")
    ],
    inputs = [
        cast_input("data_in", "eft.eval.mock_sensor_value")
    ],
    inner_structure = [link("data_in", ["accepted_out", "rejected_out"])],
    code = file("demo_filter.tar.gz"),
    code_type = "RUST_NO_STD"
)

el_main = DemoFilter
```

The developers need to provide the following parameters:

* `id` and `version` together uniquely identify an Actor Class.
* `code` includes the code and is either `file("actor_name.tar.gz")` for Rust-based Actors or `file("actor_name.wasm")` for Wasm-based Actors.
* `code_type` describes the format of the Actor and is one of the following:
  * `RUST_BASE`: The code is submitted as a Rust crate and uses the standard library. This won't be compiled into native images.
  * `RUST_NO_STD`: The code is submitted as a Rust `#![no_std]` crate. This might be compiled into a native image.
  * `WASM_BASE`: The code is compiled on the developer node and submitted as a .wasm file. The controller won't modify this code.
* `outputs` lists the Actor's output ports. It's an array containing zero or more of the following definitions:
  * `cast_output("output_name", "request_type_name")`
  * `call_output("output_name", "request_type_name", "response_type_name")`
* `inputs` lists the Actor's input ports. It's an array containing zero or more of the following definitions:
  * `cast_input("input_name", "request_type_name")`
  * `call_input("input_name", "request_type_name", "response_type_name")`
* `inner_structure` links together input and output ports. It's an array containing one or more of the following definitions:
  * `source("output_name")`: Marks the output port as a source port. This implies that the output will be serviced by a side-effect and therefore won't be removed if there is no input linked to it.
  * `sink("input_name")`: Marks the input port as a sink. Analogous to a source port, this is expected to trigger a side-effect and won't be removed.
  * `link("input_name", ["output_name", "output_2"])`: Indicates that a message to the input port may trigger zero or more of the output ports. The system will remove unused interactions based on this information.

## Rust-Based Actor Implementation

Actor developers fundamentally need to create handlers for incoming events.
These are the methods in the trait `ActorNameAPI` generated by `edgeless_function::generate!(ActorName);`.

Every Actor needs to implement the following handlers:

* `fn handle_init(payload: Option<&[u8]>, serialized_state: Option<&[u8]>) {}`: This is called when the Actor is started. `payload` represents the content passed to the `init-payload` annotation set when creating a logical instance of an Actor in the Application description.
* `fn handle_stop() {}`: This is called when the Actor is stopped.
* `fn handle_internal(data: &[u8]) {}`: This is triggered by internal side-effects, commonly `delayed_cast` (e.g., `delayed_cast(1000 "self", &1u64.to_le_bytes())`. Adding a `delayed_cast` to the init handler and this handler will create a periodic task.

Furthermore, the Actors need to implement a handler for each input port. Those handlers contain the input's name and are different for `cast` and `call` handlers---the latter require a return value:

`fn handle_cast_input_name(src: InstanceId, message: String) {}`: A `cast` handler receives the instance id of the sender and the deserialized message---this is a String in the example above, but could be any struct implementing `edgeless_function::Deserialize`.

`fn handle_call_input_name_2(_src: InstanceId, req: edgeless_function_types::http::EdgelessHTTPRequest) -> edgeless_function_types::http::EdgelessHTTPResponse {}`: A `call` handler receives the same inputs as a cast handler but also requires a return value. The framework handles serialization and the return value needs to implement `edgeless_function::Serialize`.

The types of both input and output parameters need to be mapped to the type names defined in the Starlark-based description. The trait requires a set of `type` definitions where the developers map the type names to Rust types implementing `edgeless_function::{Serialize, Deserialize}`. For the following inputs defined in the Actor's Starlark description

```star
inputs = [
  cast_input("input_name", "string")
  call_input("input_name_2", "eft.http.request", "eft.http.response"),
]
```
 the framework requires the following Rust type definitions in the trait implementation:

```rust
type EFT_HTTP_REQUEST = edgeless_function_types::http::EdgelessHTTPRequest;
type EFT_HTTP_RESPONSE = edgeless_function_types::http::EdgelessHTTPResponse;
type STRING = String;
```

In their implementation of the input handlers, the developers may use any library supported by the `wasm32-unknown-unknown` and our custom `native` (this requires `#![no_std]`) targets, and can furthermore use any of the following functions:

* `cast_output_name(message: &Self::OUTPUT_TYPE)`: Send a `cast` message to the Actor's output port `output_name`. The framework will handle serialization of the outgoing message using `edgeless_function::Serialize`.
* `call_output_name_2(message: &Self::OUTPUT_TYPE) -> Result<&Self::INPUT_TYPE, ()>`: Send a `call` message to the Actor's output port `output_name_2` and wait for the response. The framework handles serialization and derserialization using `edgeless_function::{Serialize, Deserialize}`.
* `delayed_cast(delay_ms: u64, "self", msg: &[u8])`: After a delay, send a message to the calling Actor. The developers needs to handle serialization and deserialization of their message. This is received by `handle_internal`.

## Cargo.toml

For each input and output defined in the Starlark-based Actor description, Cargo.toml needs to contain a feature `output_output_name` / `input_input_name`. These features are used to disable unused functionality while compiling target-specific images.

If the code is submitted with `code_type = "RUST_BASE"` or other code-types that are compiled by the controller, the list of includes must contain all files required to build the function:
```toml
[package]
include = ["src/**/*", "function.json", "*.star"] 
```

Furthermore, the crate can't depend on dependencies not accessible by the controller, e.g., dependencies using a relative path.
